# maylemon.net Jekyll 마이그레이션

## 프로젝트 목적

WordPress로 운영 중인 [maylemon.net](https://maylemon.net)을 Jekyll 기반의 정적 사이트로 재구현하여 GitHub에 배포하고, 검증이 완료되면 기존 WordPress 사이트와 서버를 대체한다.

이 프로젝트의 최우선 목표는 다음과 같다.

1. 기존 사이트의 디자인과 분위기를 최대한 동일하게 재현한다.
2. 게시물, 이미지, 분류 및 기존 URL을 빠짐없이 보존한다.
3. GitHub Pages에서 안정적으로 배포되는 정적 사이트를 구축한다.
4. 검색 노출 손실을 최소화하면서 `maylemon.net` 도메인을 전환한다.
5. 이후의 글과 이미지를 Git으로 관리할 수 있게 한다.

- 한글과 영문 퍼머링크가 혼재한다.
- All in One SEO가 게시물, 페이지, 카테고리 및 태그 사이트맵을 생성한다.
- 기존 Google Analytics UA ID는 `UA-97407941-1`이다.
- GA4 측정 코드도 현재 페이지에서 확인되므로 실제 운영 계정과 연결 상태를 확인해야 한다.
- DNS는 Route 53 네임서버를 사용한다.
- 루트 도메인과 `www`가 현재 서버 IP를 가리킨다.
- 확인 당시 MX 레코드는 없었다.

## 디자인 복제 가능 범위

정적 화면 기준으로 약 90~95% 수준의 재현을 목표로 한다. Jekyll은 빌드 결과가 HTML, CSS 및 JavaScript이므로 현재 디자인을 구현하는 데 본질적인 제약은 없다.

다음 요소는 높은 수준으로 재현할 수 있다.

- 고정 사이드바와 모바일 헤더
- 로고, 메뉴 및 검색 UI
- 배경색, 카드, 그림자, 여백 및 타이포그래피
- 상단 슬라이더
- masonry 카드 레이아웃
- 텍스트형 및 갤러리형 게시물
- 라이트박스
- 카테고리와 태그 화면
- 정적 검색
- Load More 또는 클라이언트 측 페이지네이션
- 이전 글, 다음 글 및 관련 글

WordPress 서버에 의존하는 다음 기능은 동일한 방식으로 동작하지 않는다.

- 댓글 작성
- AJAX 좋아요 증가
- WordPress 검색 자동완성
- 서버 요청 기반 무한 스크롤
- WordPress 관리자 화면을 통한 편집

댓글은 현재 0개이므로 댓글 UI를 제거하거나 외부 서비스를 도입할 수 있다. 기존 좋아요 수는 정적 값으로 보존할 수 있지만, 새 좋아요를 받으려면 별도 백엔드가 필요하다. 검색과 글 더 보기는 정적 JSON 인덱스와 JavaScript로 유사하게 구현할 수 있다.

기존 테마의 코드와 상용 에셋은 그대로 복사하지 않는다. 테마 라이선스를 확인하고, 필요한 디자인은 측정값과 기준 화면을 바탕으로 새로 구현한다.

## URL과 파일 보존 원칙

### 게시물 URL

모든 게시물에 기존 WordPress 경로를 명시적인 `permalink`로 기록한다. 한글 슬러그를 Jekyll의 자동 변환에 맡기면 인코딩이나 경로가 달라질 수 있다.

예:

```yaml
permalink: /카메라타/
```

최종 빌드에서는 브라우저와 서버가 처리하는 URL 인코딩까지 기존 주소와 비교해야 한다.

### 이미지 URL

가능하면 기존 이미지 경로를 그대로 보존한다.

```text
/wp-content/uploads/YYYY/MM/filename.jpg
```

이를 통해 검색엔진에 등록된 이미지와 외부에서 직접 참조하는 기존 링크가 깨지는 것을 줄인다. 최적화한 WebP 등의 파생본을 추가하더라도 기존 원본 URL은 유지한다.

### 분류 URL

기존 카테고리 및 태그 경로를 재현한다. 구조를 변경해야 할 경우 기존 주소에서 새 주소로 연결되는 리디렉션 또는 호환 페이지를 준비한다.

## 실행 계획

### 1. 백업과 콘텐츠 인벤토리

- WordPress DB, WXR 및 업로드 원본을 백업한다.
- 모든 게시물, 페이지, 카테고리, 태그 및 이미지 URL을 목록화한다.
- 게시물별 대표 이미지와 첨부 이미지 순서를 확인한다.
- 기존 URL의 HTTP 상태와 canonical 정보를 저장한다.
- 현재 화면을 주요 해상도별로 캡처한다.

이 단계의 결과물은 마이그레이션 전후를 비교하는 기준 데이터가 된다.

### 2. 디자인 기준 수립

- 데스크톱, 태블릿 및 모바일 화면을 각각 측정한다.
- 사이드바와 본문 폭, 여백, 색상, 그림자 및 글꼴을 디자인 토큰으로 정리한다.
- 홈, 텍스트 게시물, 갤러리 게시물, 카테고리, 태그, 검색 및 404 화면을 기준 템플릿으로 선정한다.
- 상용 테마에 포함된 이미지와 아이콘의 라이선스를 확인한다.

### 3. Jekyll 프로젝트 구축

- Git 저장소와 Jekyll 기본 구조를 생성한다.
- `_config.yml`, Gemfile 및 빌드 스크립트를 작성한다.
- 공통 레이아웃, 헤더, 사이드바 및 카드 컴포넌트를 구현한다.
- GitHub Actions 배포 환경을 구성한다.
- 개발 주소와 실제 도메인 환경 설정을 분리한다.

### 4. 디자인 우선 프로토타입

실제 콘텐츠 전체를 옮기기 전에 소수의 대표 콘텐츠로 디자인을 먼저 검증한다.

- 홈 화면과 상단 슬라이더
- masonry 게시물 카드
- 텍스트형 게시물 상세
- 다중 이미지 갤러리형 게시물 상세
- 데스크톱과 모바일 내비게이션
- 라이트박스 및 Load More

원본과 신규 화면을 같은 해상도로 캡처하여 겹쳐 비교하고 차이를 조정한다.

### 5. 마이그레이션 도구 작성

반복 실행 가능한 변환 스크립트를 작성한다.

- WXR 또는 DB에서 게시물을 추출한다.
- 본문 HTML을 Markdown 또는 정리된 HTML로 변환한다.
- 제목, 작성일, 수정일, 작성자, 카테고리 및 태그를 보존한다.
- 기존 URL을 `permalink`로 기록한다.
- 대표 이미지와 첨부 이미지를 연결한다.
- 사진 게시물의 갤러리와 이미지 순서를 복원한다.
- 내부 링크와 이미지 경로를 변환한다.
- 누락, 중복 및 변환 실패 리포트를 생성한다.

마이그레이션 스크립트는 최종 전환 직전의 변경분을 다시 반영할 수 있도록 여러 번 실행 가능해야 한다.

### 8. 시험 배포

- 먼저 GitHub Pages 임시 주소에 배포한다.
- 시험 사이트는 검색엔진에 색인되지 않도록 설정한다.
- WordPress와 신규 사이트를 URL별로 비교한다.
- 사용자 검수가 완료된 뒤 콘텐츠를 동결한다.
- 동결 후 마지막 변경분을 다시 마이그레이션한다.

### 9. 도메인 전환

- 전환 24~48시간 전에 DNS TTL을 낮춘다.
- Route 53 네임서버는 유지한다.
- GitHub Pages에 사용자 도메인을 등록하고 소유권을 검증한다.
- 루트 도메인의 A 레코드를 GitHub Pages로 변경한다.
- `www`를 GitHub Pages 호스트로 연결한다.
- 인증서 발급 후 HTTPS를 강제한다.
- HTTP/HTTPS 및 루트/`www` 정규화를 확인한다.
- Search Console에서 sitemap을 다시 제출한다.

### 10. 안정화와 WordPress 종료

- 전환 후 오류 로그와 Search Console 색인 상태를 확인한다.
- 기존 WordPress 서버는 최소 2~4주 동안 롤백용으로 보존한다.
- 이상이 없으면 서버를 종료하되 DB와 업로드 백업은 별도로 보관한다.
- 새 글 작성, 이미지 추가, 로컬 미리보기 및 배포 방법을 문서화한다.

## 완료 기준

- `maylemon.net`이 GitHub Pages에서 HTTPS로 제공된다.
- 주요 화면이 기존 디자인과 시각적으로 구분하기 어려운 수준이다.
- 기존 게시물 및 페이지 URL이 유지된다.
- 게시물 45개와 모든 공개 사진이 이전된다.
- 깨진 이미지와 내부 링크가 없다.
- 카테고리, 태그, sitemap 및 RSS가 제공된다.
- GitHub에 반영된 변경이 자동으로 빌드 및 배포된다.
- WordPress 서버 없이 사이트가 정상 동작한다.
- 백업, 복구 및 콘텐츠 작성 절차가 문서화되어 있다.

## 주요 위험과 대응

### 사진 게시물 누락

공개 REST API만 사용하지 않고 DB, WXR 및 업로드 원본을 함께 사용한다. 게시물별 첨부 관계와 표시 순서를 별도 검증한다.

### URL 변경에 따른 검색 노출 하락

모든 게시물에 기존 경로를 명시하고 이미지 경로도 보존한다. 변경이 불가피한 주소는 호환 페이지 또는 리디렉션 정책을 마련한다.

### 테마 라이선스

기존 상용 테마 코드를 무단 복사하지 않는다. 소유한 라이선스의 허용 범위를 확인하고, 레이아웃과 스타일은 독립적으로 재구현한다.

### GitHub 저장소 용량

이미지 전체 용량과 개별 파일 크기를 사전에 측정한다. GitHub의 개별 파일 및 저장소 제한을 초과하는 경우 이미지 최적화 또는 별도 저장소 사용을 검토하되 기존 URL 호환성을 유지한다.

### 정적 사이트의 기능 한계

댓글, 좋아요 및 서버 검색이 반드시 필요한지 먼저 결정한다. 필요한 경우에만 외부 서비스나 서버리스 백엔드를 추가한다.

## 착수 전에 결정할 사항

1. 기존 디자인 복제 시 허용할 차이의 범위
2. GitHub 계정, 저장소 이름 및 공개 여부
3. WordPress 관리자, DB 및 파일 백업 접근 가능 여부
4. Route 53과 GitHub 도메인 설정 권한
5. 댓글 영역 유지 여부
6. 좋아요 수 표시 및 신규 좋아요 기능 필요 여부
7. GA4 유지, 교체 또는 분석 기능 제거 여부
8. 향후 콘텐츠를 Markdown으로 직접 작성할지 별도 편집 도구를 둘지

## 권장 진행 순서

```text
전체 백업
→ 콘텐츠와 디자인 인벤토리
→ Jekyll 기반 구축
→ 디자인 프로토타입
→ 마이그레이션 도구
→ 전체 콘텐츠 적용
→ 자동 및 시각 검증
→ 시험 배포
→ DNS 전환
→ 안정화 및 WordPress 종료
```
